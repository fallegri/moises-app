# PostgreSQL persistence and Vercel/Railway deployment scaffold

This change migrates the backend persistence layer from JSON files to PostgreSQL (via synchronous SQLAlchemy with psycopg2), adds deployment configuration for Railway (backend) and Vercel (frontend), and introduces a factory pattern that falls back to JSON when `DATABASE_URL` is absent. The approach preserves the existing in-memory-plus-persistence architecture unchanged — routers still hold state in module-level dicts and serialize to the persistence layer — while swapping the storage backend beneath it. The CORS configuration now dynamically includes `FRONTEND_URL` for the deployed frontend.

Watch for: AI config router imports the persistence service but never calls it — the save/load still use raw file I/O (confirmed). The PostgreSQL session management opens a new connection for every operation with no connection pooling tuning or context-manager pattern, creating a resource leak risk under load (confirmed). `coherence_validated` is stored as a string "true"/"false" rather than a boolean column, introducing fragile string-comparison semantics (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The persistence layer gained a strategy split: `get_persistence_service()` returns either `JsonPersistenceService` or `PostgresPersistenceService` based on the presence of `DATABASE_URL`. Both implement the same duck-typed interface (no ABC or Protocol enforces this). The Postgres implementation maps the Pydantic models to SQLAlchemy ORM classes that store complex nested data as JSONB columns, which is a pragmatic choice for a schema that changes frequently.

The AI config router (`ai_config.py`) instantiates the persistence service at module level but continues to use its own `load_ai_config()` / `save_ai_config()` functions that read/write directly to the filesystem. AI config is never persisted to PostgreSQL in production despite the infrastructure being in place — it will be lost on Railway's ephemeral disk between deploys.

Session management in `persistence_postgres.py` creates a fresh `Session` per method call via `get_session()`, commits or rolls back, then closes. There is no connection pool size configuration, no statement timeout, and no reuse across related operations within a single request. Under concurrent load this will exhaust NeonTech's default connection limit (typically low on free/starter plans).

1. **AI config not routed through persistence service** — `ai_config.py` still calls its own `load_ai_config()`/`save_ai_config()` functions that read/write to disk. 4. **`coherence_validated` stored as string** — `WorkflowStateDB.coherence_validated` is `Column(String)` holding "true"/"false". Use `Column(Boolean)` and convert at the serialization boundary to avoid case-sensitivity bugs.
5. **`_parse_datetime` silently masks bad data** — When datetime parsing fails, `_parse_datetime` returns `datetime.utcnow()` instead of raising or logging. This hides data integrity issues (e.g., a corrupted `created_at` field is silently overwritten with "now").

## AI config persistence gap

The `ai_config.py` router imports `get_persistence_service` and assigns it to `_persistence` at module level, but neither `load_ai_config()` nor `save_ai_config()` (defined as module-level functions in the same file) use it. They read/write `_CONFIG_FILE` directly:

```python
_persistence = get_persistence_service()  # imported but unused

def load_ai_config() -> Optional[dict]:
    if not _CONFIG_FILE.exists():
        return None
    data = json.loads(_CONFIG_FILE.read_text(encoding="utf-8"))
    return data

def save_ai_config(config: dict) -> None:
    _CONFIG_FILE.write_text(json.dumps(config, ...), ...)
```

When `DATABASE_URL` is set, `_persistence` will be a `PostgresPersistenceService` with `save_ai_config` and `load_ai_config` methods ready to use, but the router never calls them. AI configuration is always stored on the local filesystem regardless of the persistence backend, and will be lost on Railway's ephemeral disk between deploys.

## Session lifecycle and connection pressure

`PostgresPersistenceService` opens a new session for each method. A single `POST /api/workflow/{id}/submit-input` request triggers `_persist_workflow` and `_persist_project`, each of which opens its own session independently.

The engine is created with `pool_pre_ping=True` but no `pool_size` or `max_overflow` parameters. SQLAlchemy defaults to `pool_size=5` and `max_overflow=10`. NeonTech's free tier often limits to 5-10 simultaneous connections total. Under moderate concurrency the pool may saturate, and requests will block or fail with connection-limit errors. Adding explicit pool parameters and considering a request-scoped session (via FastAPI's dependency injection) would address both the connection pressure and the overhead of session creation per call.

## Boolean-as-string in WorkflowStateDB

`WorkflowStateDB.coherence_validated` is declared as `Column(String)` and populated with `str(workflow_data.get("coherence_validated", False)).lower()`. The read path compares `db_workflow.coherence_validated == "true"`. Any casing variation or unexpected value ("True", "1", etc.) will silently evaluate to `False`. A `Column(Boolean)` with proper Python bool assignment would be safer and eliminate a class of comparison bugs.

## No formal interface contract

Both persistence implementations expose the same method signatures, but nothing enforces this at the type level. If a method is added to one and not the other, the failure only manifests at runtime when the factory returns the wrong backend. A `typing.Protocol` class would catch this statically:

```python
class PersistenceProtocol(Protocol):
    def save_project(self, project_id: str, project_data: dict[str, Any]) -> None: ...
    def load_project(self, project_id: str) -> Optional[dict[str, Any]]: ...
    # etc.
```

## Test coverage gap for Postgres path

All 75 tests pass using the JSON fallback. There are no tests for `PostgresPersistenceService` — the entire Postgres code path is untested. The first integration test happens in staging. Consider adding at least one round-trip test using a SQLite in-memory backend (JSONB columns would need a workaround or mock) to verify serialization correctness before deploying.
