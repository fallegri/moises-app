# AI-powered research assistant with 12-phase workflow

A full-stack application that guides a researcher step-by-step through problem identification, refinement, question formulation, state-of-art analysis, objectives, methodological framework, and instrument design — validating coherence at each gate. The backend is Python/FastAPI with an OpenAI-compatible AI layer and a 42-book knowledge base; the frontend is React/Vite/Tailwind with a stepper UI, file uploads, and document download. Docker Compose ties them together through an nginx reverse proxy.

Watch for: the frontend and backend disagree on URL paths (`/api/projects` vs `/projects`), making the app non-functional at runtime (confirmed). Coherence validation defaults to `true` when the AI response is ambiguous, meaning an incoherent project can advance silently (confirmed). All state is in-memory with no persistence — a server restart loses every project (confirmed). Knowledge upload extracts text but never persists it to the knowledge base, so uploaded literature disappears (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The frontend API client prefixes every call with `/api/` (e.g. `/api/workflow/{id}/status`), but FastAPI mounts routers without that prefix (`/workflow/{id}/status`). Neither the Vite dev proxy nor the nginx production config strips the prefix, so no HTTP request from the frontend will ever reach a backend route. This is a blocking integration bug.

All projects, workflow states, and generated documents live in module-level Python dicts. There is no database, no file-backed persistence, no session affinity. A single process restart or scale-out event erases all user work. For a prototype this may be intentional, but the README presents the system as deployable, and the Docker Compose offers `restart: unless-stopped` — which will silently wipe state.

The coherence validation gate — the mechanism that prevents a researcher from advancing with inconsistent data — parses free-form AI text looking for keywords like "coherente" or "incoherente". When the AI response contains neither, the system returns `True`, advancing the workflow. This fail-open default undermines the core guardrail the application advertises.

The knowledge upload endpoint parses a file and returns a preview, but the extracted text is never added to the `KnowledgeBaseService` document list. A user who uploads supplementary literature will see a success message but the content will never appear in searches or be used as AI context.

The AI service instantiates an `OpenAI` client at import time with whatever is in `settings.ai_api_key`. When the key is the default empty string (no `.env` file), the client is still created. Calls will fail at runtime with an opaque provider error rather than a clear startup diagnostic.

<summary>Issues (7)</summary>

1. **Frontend/backend path mismatch** — Frontend sends to `/api/projects`, `/api/workflow/...`, etc. Backend mounts at `/projects`, `/workflow/...`. No path rewrite exists in either proxy layer. Fix: add `rewrite` to Vite proxy config and add a proper `location /api/ { rewrite ^/api(/.*)$ $1 break; ... }` in nginx, or mount all backend routers under an `/api` prefix.
2. **Coherence validation defaults to pass** — `_parse_coherence_result` returns `True` when no keyword matches. Fix: default to `False` (fail-closed) so ambiguous AI responses block advancement rather than silently passing.
3. **No persistence layer** — Projects, workflows, and documents are in-memory dicts. Any restart loses all data. Minimum fix for production: add SQLite/PostgreSQL or file-backed storage.
4. **Knowledge upload is a no-op** — Parsed text is returned to the client but never stored or indexed. Fix: append the parsed content as a new `KnowledgeDocument` in the service's `documents` list (and persist to disk).
5. **No API key validation at startup** — Empty `ai_api_key` creates an `OpenAI` client that will fail on first call. Fix: raise on startup or on first request with a clear error when the key is empty.
6. **Frontend submit sends multipart/form-data, backend expects JSON body** — `submitInput` on the frontend sends FormData, but the backend `SubmitInputRequest` is a Pydantic `BaseModel` parsed from JSON. The request will fail with a 422. Fix: align on one content type (accept form-data in the backend or send JSON from the frontend).
7. **State-of-art "no more studies" checkbox has no backend path** — The user requirement specifies a checkbox for "no more investigations found" to accept fewer than 6. The `StateOfArtMatrix` model has a `no_more_studies_found` boolean, but no workflow endpoint or engine logic reads or sets it.

## URL routing gap between frontend and backend

The frontend Axios client sets `baseURL` from `VITE_API_URL` (defaults to empty string) and prepends `/api/` to every route:

```typescript
// frontend/src/api/client.ts
const api = axios.create({ baseURL: import.meta.env.VITE_API_URL || '' })
// ...
const response = await api.post('/api/projects', data)
```

The backend registers routers directly:

```python
# backend/app/main.py
app.include_router(projects.router, prefix="/projects", ...)
```

The Vite dev proxy sends `/api` to `http://localhost:8000` without rewriting:

```typescript
proxy: { '/api': { target: 'http://localhost:8000', changeOrigin: true } }
```

A request to `/api/projects` arrives at the backend as `/api/projects`. FastAPI has nothing mounted there — 404. The nginx config has the same problem: `location /api/ { proxy_pass http://backend:8000/api/; }` forwards the `/api/` prefix intact.

## Coherence validation fail-open

```python
# backend/app/services/workflow_engine.py
def _parse_coherence_result(self, result: str) -> bool:
    # ...checks negative then positive keywords...
    # Default to true if no clear indicator
    return True
```

If the AI returns a nuanced response that doesn't contain the exact Spanish keywords ("coherente", "incoherente", "valido", "invalido"), the system passes coherence. Given that the prompt instructs the AI to start with "COHERENTE" or "INCOHERENTE", this might work when the AI follows instructions perfectly, but any model deviation (JSON-wrapped response, English response, timeout truncation) will silently pass.

## In-memory state and restart semantics

```python
# backend/app/routers/projects.py
_projects: dict[str, ResearchProject] = {}

# backend/app/routers/workflow.py
_workflow_states: dict[str, WorkflowState] = {}

# backend/app/routers/documents.py
_generated_documents: dict[str, dict[str, bytes]] = {}
```

These module-level dicts are the only storage. Docker Compose sets `restart: unless-stopped`, so a crash-restart cycle will bring the server back with empty state. Multi-worker deployments (e.g. `uvicorn --workers 4`) would also fragment state across processes.

## Knowledge upload dead end

```python
# backend/app/routers/knowledge.py — upload endpoint
extracted_text = _file_parser.parse_file(content, file.filename)
return { "filename": ..., "extracted_text_length": ..., "preview": ..., "message": ... }
```

The extracted text is returned but never written to disk or appended to `_knowledge_base.documents`. Subsequent searches will not find the uploaded content. The stated requirement is "dar la posibilidad al usuario de cargar mas literatura".

## Frontend/backend content-type disagreement on submit

The frontend `submitInput` function sends `multipart/form-data`:

```typescript
const formData = new FormData()
formData.append('text', text)
const response = await api.post(`/api/workflow/${projectId}/submit-input`, formData, {
  headers: { 'Content-Type': 'multipart/form-data' },
})
```

The backend endpoint expects a JSON body parsed into a Pydantic model:

```python
class SubmitInputRequest(BaseModel):
    text: str
    file_content: Optional[str] = None

@router.post("/{project_id}/submit-input")
async def submit_input(project_id: str, request: SubmitInputRequest):
```

FastAPI will reject the multipart payload with a 422 Validation Error because Pydantic cannot parse form fields as a JSON body model.

## Missing lifecycle for "no more studies" flag

The user requirement specifies that when fewer than 6 similar studies exist, the user should check a box to confirm no more were found. The `StateOfArtMatrix` model includes `no_more_studies_found: bool = False`, but the workflow engine's `process_input` for the `STATE_OF_ART` phase falls into the generic `else` branch (chapter generation) rather than handling study entry and the flag. No endpoint accepts the checkbox state or validates the minimum-6 constraint.
