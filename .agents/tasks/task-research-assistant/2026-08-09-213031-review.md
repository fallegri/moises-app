# AI research assistant with 12-phase workflow (v2)

Full-stack application that guides researchers through problem identification, refinement, question formulation, state-of-art analysis, objectives, and methodological framework construction. The v1 blocking issues — URL routing mismatch, fail-open coherence validation, lack of persistence, dead-end knowledge upload, missing API key validation, content-type mismatch, and state-of-art lifecycle — have all been addressed. The backend now mounts all routers under `/api/`, coherence defaults to false, persistence writes JSON to disk, uploaded literature is appended to the knowledge base, the OpenAI client validates configuration lazily, the frontend sends JSON for submit-input, and dedicated endpoints handle study addition and the "no more studies" flag.

Watch for: the frontend phase identifiers (`background`, `problem_chapter`, `data_collection`) differ from the backend enum values (`state_of_art`, `problem_identification_chapter`, `data_collection_instruments`), meaning the stepper will never match backend state for those phases (confirmed). The `StateOfArtMatrix` component manages state locally with no connection to the backend add-study/no-more-studies endpoints, so studies entered in the UI are never persisted (confirmed). Persistence covers projects and workflows but not generated documents — the `_generated_documents` dict in the documents router is still in-memory only (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The frontend defines a `PHASES` array with 12 entries whose `id` values diverge from the backend's `WorkflowPhase` enum for three phases: `background` vs `state_of_art`, `problem_chapter` vs `problem_identification_chapter`, and `data_collection` vs `data_collection_instruments`. When the backend returns `current_phase: "state_of_art"`, the frontend `findIndex` lookup against its PHASES array yields -1, breaking stepper highlighting and phase-conditional rendering (the `StateOfArtMatrix` is gated on `phase === 'background'` which will never match).

The `StateOfArtMatrix` frontend component is entirely self-contained — it holds studies in local React state and the "no more research" checkbox in a local `useState`. It never calls the backend's `POST /api/workflow/{id}/state-of-art/add-study` or `POST /api/workflow/{id}/state-of-art/no-more-studies` endpoints. Users filling out the matrix are editing a local throwaway; the data won't participate in workflow advancement or coherence validation.

Generated documents (`_generated_documents` in `documents.py`) remain in a module-level dict with no persistence layer backing. A restart loses all previously generated Word files. Unlike projects and workflows, no `PersistenceService` integration exists for documents.

The frontend `WorkflowStatus` type expects fields (`progress`, `tasks`, `options`, `ai_response`) that the backend's `/status` endpoint does not return. The backend returns `current_tasks`, `can_advance`, and `coherence_validated` instead. This will produce `undefined` accesses and a silent empty UI rather than data.

The `KnowledgeBase` component's search response handler assigns the API result (which has shape `{ query, results, total_results }`) directly to a `KnowledgeDocument[]` state. The component then iterates expecting `.id` and `.title` fields, but the backend returns `{ filename, heading, content, score }`. The search results will render empty rows.

<summary>Issues (7)</summary>

1. **Phase ID mismatch (3 phases)** — Frontend uses `background`, `problem_chapter`, `data_collection`; backend uses `state_of_art`, `problem_identification_chapter`, `data_collection_instruments`. Align the identifiers in either layer.
2. **StateOfArtMatrix disconnected from API** — Component manages state locally, never calls backend endpoints for adding studies or setting the no-more-studies flag. Wire it to the existing backend routes or lift state to the parent page.
3. **Generated documents not persisted** — `_generated_documents` dict has no disk backing. Add document persistence or accept that documents must be re-generated after restart.
4. **WorkflowStatus type/response mismatch** — Frontend expects `progress`, `tasks`, `options`, `ai_response`; backend returns `current_tasks`, `can_advance`, `coherence_validated`, `phase_info`. Align the response contract.
5. **KnowledgeBase search result shape mismatch** — Frontend expects `{ id, title, content_preview }`; backend returns `{ filename, heading, content, score }`. Map fields or update the type.
6. **Persistence volume missing in Docker** — The backend writes to `/app/storage/data/` inside the container but no volume is declared, so persisted data is lost on container recreation. Add a named volume for `STORAGE_PATH`.
7. **Single-worker deployment only** — Persistence loads data into module-level dicts at import time. Multiple Uvicorn workers or replicas will have divergent in-memory copies. Document the single-worker constraint or move to a shared store.

## Frontend-backend phase identifier divergence

The backend `WorkflowPhase` enum defines:

```python
STATE_OF_ART = "state_of_art"
PROBLEM_IDENTIFICATION_CHAPTER = "problem_identification_chapter"
DATA_COLLECTION_INSTRUMENTS = "data_collection_instruments"
```

The frontend `PHASES` array defines the corresponding slots as:

```typescript
{ id: 'background', name: 'Antecedentes', ... },
{ id: 'problem_chapter', name: 'Capitulo del Problema', ... },
{ id: 'data_collection', name: 'Recopilacion de Datos', ... },
```

In `Project.tsx`, stepper status is computed by finding the index of `workflow.current_phase` in the PHASES array. When the backend returns `"state_of_art"`, `findIndex` returns -1 because no entry has `id === "state_of_art"`. This means `currentIndex` is -1, so all phases compare as `> -1` and show "completed" — the stepper breaks entirely once the project hits the sixth phase.

The `PhaseContent` component conditionally renders the `StateOfArtMatrix` only when `phase === 'background'`. Since the backend sends `"state_of_art"`, the matrix never renders. The same pattern affects the variable matrix if `methodological_framework` matches (it does in this case) and the two other mismatched phases.

## StateOfArtMatrix is client-only

The component holds `studies` in a `useState<StudyEntry[]>([])` and `noMoreResearch` in a `useState(false)`. The backend provides `POST /api/workflow/{project_id}/state-of-art/add-study` and `POST /api/workflow/{project_id}/state-of-art/no-more-studies`, plus the `can_advance_state_of_art` check before phase advancement. None of these are invoked by the frontend.

The `advanceWorkflow` handler in `Project.tsx` calls `POST /api/workflow/{id}/advance`, which checks `can_advance_state_of_art`. That method inspects `project.state_of_art.studies` — which will always be empty because no frontend action ever populated it via the API. The user will be unable to pass the state-of-art phase through the UI.

## Generated documents have no persistence

```python
# backend/app/routers/documents.py
_generated_documents: dict[str, dict[str, bytes]] = {}
```

The `PersistenceService` handles projects and workflows but is never imported or used in `documents.py`. If the backend restarts, all generated Word files vanish. In Docker with `restart: unless-stopped`, a crash wipes all documents with no user-visible warning.

## WorkflowStatus response contract mismatch

The backend's `get_workflow_status` returns:

```python
{
    "project_id": ...,
    "current_phase": ...,
    "phase_info": { "title": ..., "description": ... },
    "completed_phases": [...],
    "current_tasks": [{ "description": ..., "instruction": ..., "completed": ... }],
    "coherence_validated": ...,
    "can_advance": ...,
}
```

The frontend `WorkflowStatus` type expects:

```typescript
{
  project_id: string
  current_phase: PhaseId
  phases: Phase[]
  tasks: Task[]
  progress: number
  ai_response?: string
  options?: string[]
}
```

There is no `progress` field from the backend, no `phases` array, no `ai_response`, and no `options`. The `tasks` field maps to `current_tasks` by a different key name and different shape (backend has `instruction`, frontend expects `id`). The sidebar progress bar (`workflow.progress`) will be `undefined`, rendering 0% permanently.

## Knowledge search response shape mismatch

The `KnowledgeBase.tsx` component calls `searchKnowledge(query)` which hits `GET /api/knowledge/search?q=...`. The backend returns:

```json
{ "query": "...", "results": [{ "filename": "...", "heading": "...", "content": "...", "score": 5 }], "total_results": 1 }
```

The client function assigns `response.data` (the entire envelope) to a `KnowledgeDocument[]` type. It should extract `response.data.results`. Furthermore, the component iterates with `doc.id` and `doc.title` which don't exist on the backend response objects (`filename` and `heading` are the closest equivalents). The React key will be `undefined` and the rendered `<h5>` will be empty.

## Docker volume gap for persistence

The `docker-compose.yml` mounts `./skills/knowledge:/app/knowledge:ro` for the knowledge base but declares no volume for `/app/storage`. The `PersistenceService` writes to `/app/storage/data/`. Container recreation (via `docker-compose up --force-recreate` or image rebuild) deletes the writable layer, erasing all persisted projects and workflows.
