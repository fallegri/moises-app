# Frontend UX feedback for knowledge base and phase submission (v2)

Follow-up pass verifying the five issues flagged in v1. Commit `88f7da5` resets the submit-input mutation on advance (`submitInput.reset()` inside `advanceWorkflow.mutate`'s `onSuccess`), which clears `submitInput.data` and `isSuccess` so the success banner, the phase-1 identified-problem block, the coherence button gating, and the blocked-advance message now all reflect only the current phase. The upload `accept` filter gained `.txt` to match the backend's supported set, multi-file upload became per-file resilient with partial-failure reporting and an unconditional list refresh, and coverage was added for both cross-phase staleness and the knowledge base upload/list behavior (21 tests passing).

Watch for: one low-severity carryover — the backend appends uploads to its document list without de-duplicating filenames, so re-uploading the same name yields duplicate entries whose React `key={doc}` collide (possible). Nothing blocking.

**Verdict**: APPROVED

## High-level view

The central v1 bug — stale submit-mutation state bleeding across phase boundaries — is fixed at the right place. `handleAdvance` now calls `submitInput.reset()` in the advance mutation's `onSuccess`, so the single page-lifetime mutation no longer carries phase-1 state into phase 2+. Because every derived signal (banner, identified-problem block, coherence button in `Project.tsx`, and the blocked-advance branch in `PhaseContent`) reads from that one mutation, resetting it corrects all four symptoms at once, including the message inversion where a fresh phase told the user to "valida la coherencia" instead of "envia informacion."

The upload `accept` filter is now `.md,.docx,.xlsx,.txt`, matching the backend's `SUPPORTED_EXTENSIONS`. Multi-file upload wraps each file in its own try/catch, tallies uploaded vs failed, surfaces a red partial-failure state, and refreshes the document list unconditionally so successful files appear even when part of the batch fails.

Test coverage closed both v1 gaps: two new `PhaseContent` tests assert that a reset (`submitResult: null`) against a new phase shows the submit message and hides the identified-problem block, and a new `KnowledgeBase.test.tsx` covers mount list rendering, empty state, multi-file success, and partial failure.

The in-memory backend document list is unchanged (per instruction); it still resets on backend restart and isn't cross-process. That same store appends filenames without de-duplication, which the new list feature now makes visible as a minor React key concern.

### Stale submit state reset on advance (issues 1 & 2 resolved)

The fix lands in `handleAdvance`:

```tsx
const handleAdvance = () => {
  advanceWorkflow.mutate(undefined, {
    onSuccess: () => {
      submitInput.reset()
      setValidationResult(null)
    },
  })
}
```

`submitInput.reset()` clears `data` and `isSuccess`, the sole inputs to every per-phase signal, so all four v1 symptoms clear together. In `PhaseContent` the blocked-message branch now evaluates against a null `submitResult` after advancing, so a fresh phase shows "Primero envia informacion para esta fase" rather than the inverted "Primero valida la coherencia." The phase-1 identified-problem block and success banner (both gated on `submitResult`) no longer render in later phases, and the coherence button in `Project.tsx` (gated on `submitInput.isSuccess`) hides again until the user submits in the new phase.

The call-level `onSuccess` coexists with the hook-level `onSuccess` in `useAdvanceWorkflow` (the workflow-query invalidation); React Query runs both, so the reset does not suppress the refetch — worth confirming since suppressing it would strand the UI on the old phase. `setValidationResult(null)` additionally clears a stale coherence result that would otherwise linger. Confirmed by reading `Project.tsx`, `useWorkflow.ts`, and `PhaseContent.tsx`.

### Upload accept filter and resilient multi-upload (issues 3 & 4 resolved)

The picker `accept` is now `.md,.docx,.xlsx,.txt`, matching `FileParser.SUPPORTED_EXTENSIONS = {".docx", ".xlsx", ".md", ".txt"}`. Multi-upload no longer aborts the batch on first failure:

```tsx
for (const file of Array.from(files)) {
  try { await uploadKnowledge(file); uploaded++ }
  catch { failed++ }
}
```

Counts drive the messaging — green "N archivos subidos exitosamente", and red "N subidos, M fallaron" (or a plain error when nothing succeeded). `loadDocuments()` moved to `finally`, so the list refreshes regardless of partial failure and the input resets to allow re-selecting the same files. The failure path that previously discarded progress and skipped the refresh is gone.

### Document-list de-duplication (new, low severity)

`list_knowledge_documents` returns `get_all_filenames()`, which maps directly over `_knowledge_base.documents`, and `upload_literature` does `_knowledge_base.documents.append(new_doc)` with no de-dup. Uploading a file whose name already exists appends a second entry, so the frontend list renders two `<li key={doc}>` with the same key, producing a React duplicate-key warning (possible — depends on whether users re-upload same-named files in a session). Not introduced by this diff's frontend code, but the list feature is what makes it observable. De-dup on append, or key on `${doc}-${index}`, if this becomes noticeable.

### Test coverage (issue 5 resolved)

`PhaseContent.test.tsx` adds two tests simulating the post-advance reset: with `submitResult: null` against a new `current_phase`, one asserts "Primero envia informacion" shows and the coherence message does not, the other asserts the identified-problem block is absent — directly exercising the inversion v1 flagged. `KnowledgeBase.test.tsx` mocks the client and covers mount-time list rendering, empty state, multi-file success (two `uploadKnowledge` calls, "2 archivos subidos exitosamente", refreshed list), and partial failure ("1 subidos, 1 fallaron" with the list still refreshed). Not tested: the document-list de-dup case above, consistent with it being an unmodified backend behavior.
