# Frontend UX feedback for knowledge base and phase submission

Four intuitiveness improvements to the research workflow UI: multi-file upload with a visible list of already-loaded documents in the knowledge base, a green confirmation plus the AI-identified problem after submitting phase-1 text, gating the "Validar Coherencia" button behind a successful submit, and an amber contextual message explaining why the advance button is disabled. The approach reuses existing backend endpoints (none were modified) and threads the submit-input response through `PhaseContent` via a new `submitResult` prop and a `SubmitInputResponse` type. The submit-input return type in `client.ts` was also corrected from `WorkflowStatus` to the actual response shape.

Watch for: the submit-input mutation state is never reset when advancing to the next phase (confirmed), so the phase-1 success banner, the coherence button, and the blocked-message logic all carry over into later phases with stale data. The upload `accept` filter and the visible document list also have gaps worth a look (confirmed / likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The core of the change lives in `PhaseContent`, which now receives the raw submit-input response and derives three things from it: a success banner, the AI-identified problem (phase 1 only), and a message explaining why advancing is blocked. The gating for the coherence button was lifted up into `Project.tsx`, keyed off `submitInput.isSuccess`.

The design leans entirely on React Query mutation state (`submitInput.data` / `.isSuccess`) as the signal for "the user has submitted input in this phase." That signal is per-mutation, not per-phase, and nothing resets it on advance. As a result the confirmation UI, the coherence button, and the "valida la coherencia" hint bleed across phase boundaries — the strongest concern in this change.

The knowledge base upload now loops over multiple files and refreshes a document list from `GET /api/knowledge/documents`. The list reflects in-memory backend state (uploads are appended to a list, not persisted), and the client-side `accept` filter is narrower than what the backend accepts. Multi-file upload is sequential and non-atomic, with a partial-failure path that discards progress feedback.

Tests cover the four `PhaseContent` message states but not the cross-phase staleness, and there is no coverage for the knowledge base changes.

<summary>Issues (5)</summary>

1. **Stale submit state across phases** — `submitInput.data`/`isSuccess` is never reset on advance, so the phase-1 success banner, identified-problem block, coherence button, and "valida la coherencia" hint persist into later phases. Call `submitInput.reset()` in the advance flow (or key the signal on `current_phase`).
2. **Blocked-message logic is phase-blind** — once anything has been submitted, a fresh phase shows "Primero valida la coherencia" instead of "Primero envia informacion," because the message derives from mutation state rather than the new phase's actual input. Fix follows from resetting/rekeying the submit signal.
3. **Upload accept filter narrower than backend** — input `accept=".md,.docx,.xlsx"` omits `.txt`, which the backend allows. Add `.txt` (or intentionally document the restriction).
4. **Partial-failure feedback on multi-upload** — a mid-batch failure shows a generic "Error al subir el archivo" and skips `loadDocuments()`, hiding the files that did succeed. Report count uploaded vs failed and refresh the list regardless.
5. **No tests for new behavior beyond messages** — cross-phase staleness and the KnowledgeBase multi-upload/document-list changes are untested.

<summary>Details</summary>

### Submit-input response threaded through PhaseContent

`submitInput`'s declared return type in `client.ts` previously claimed `WorkflowStatus` — a real type bug, since the endpoint returns the submit result, not workflow status; the new `SubmitInputResponse` (`{ phase, result, message }`) matches the actual payload. `PhaseContent` derives the AI problem only when `result.identified_problem` is a string, which is load-bearing: `process_input` returns `identified_problem` exclusively in the `PROBLEM_IDENTIFICATION` phase, while other phases return unrelated keys (`refined_formulations`, `research_questions`, etc.). Without that guard the block would either mis-render or never show in later phases.

### Stale mutation state bleeds across phase transitions

The "has the user submitted input in this phase?" signal is `submitInput.data` (in `PhaseContent`) and `submitInput.isSuccess` (in `Project.tsx`). Both come from a single React Query mutation whose lifetime spans the whole `Project` page, and nothing resets it when the user advances:

```
phase 1: submit text ──► submitInput.data set, isSuccess=true
         │  success banner shows, coherence button shows  (correct)
         ▼
  advance ──► workflow refetched (new phase), but submitInput.data unchanged
         │
phase 2: submitInput.data STILL set from phase 1
         ├─ success banner + phase-1 "Problema identificado" still render
         ├─ "Validar Coherencia" button visible with no phase-2 submit
         └─ advanceBlockedMessage = "Primero valida la coherencia"
            (should be "Primero envia informacion")
```

In `PhaseContent` the blocked-message branch is `if (submitResult && !coherence_validated)` → "valida la coherencia", `else if (!submitResult)` → "envia informacion". After advancing, `submitResult` is still truthy from the prior phase, so a brand-new phase where the user has submitted nothing tells them to validate coherence instead of to submit input — the opposite of requirement 4's intent. The phase-1 identified-problem banner keeps rendering in phase 2+, and the coherence button in `Project.tsx` appears before any submission in the new phase.

The fix is to reset the mutation when advancing — `submitInput.reset()` in `handleAdvance` (or in the advance mutation's `onSuccess`) — or to derive the per-phase signal from something keyed on `workflow.current_phase` rather than a page-lifetime mutation. Confirmed by reading `Project.tsx` (mutation is never reset), `useWorkflow.ts` (advance only invalidates the workflow query), and `PhaseContent.tsx` (message logic).

### Knowledge base multi-upload and document list

Multi-upload iterates `Array.from(files)` and awaits each `uploadKnowledge` call in sequence, then refreshes the list via `getKnowledgeDocuments()` and resets `e.target.value` so re-selecting the same files re-triggers `onChange`. Two gaps:

The `accept` attribute is `.md,.docx,.xlsx`, but the backend's `upload` endpoint allows `{.docx, .xlsx, .md, .txt}`. A `.txt` file the backend would accept can't be chosen through the picker. Either add `.txt` or treat the narrower client filter as intentional.

The batch is non-atomic and its failure path loses information. On any file's failure the loop aborts into the generic `'Error al subir el archivo'` message, `loadDocuments()` in the try block is skipped, so the list doesn't reflect files that uploaded before the failure, and the `uploaded` count is discarded. A partial batch should report how many succeeded and still refresh the list (moving `loadDocuments()` to `finally`, or reporting per-file outcomes).

Not a regression, but worth knowing: the backend appends uploaded docs to an in-memory list (`_knowledge_base.documents.append`) and `get_all_filenames()` reads that list, so the "Documentos cargados" view resets on backend restart and won't reflect uploads across processes. The document-list feature satisfies requirement 1 for a live session but isn't backed by persistence.

### Coherence button gating

Requirement 3 is met by wrapping the validation block in `{submitInput.isSuccess && (...)}` in `Project.tsx`. This shares the reset problem above: because `isSuccess` never clears, the button stays visible after advancing into a phase where nothing has been submitted yet. Resetting the mutation on advance fixes both symptoms together.

### Test coverage

`PhaseContent.test.tsx` covers the four message/confirmation states: the pre-submit "envia informacion" hint, the post-submit "valida la coherencia" hint, the success message, the AI-identified-problem block, and suppression of blocked messages when `can_advance` is true. Not tested: the cross-phase staleness (a test rendering a `submitResult` from a prior phase against a new `current_phase` would have surfaced the blocked-message inversion), and anything in `KnowledgeBase` — multi-file loop, document list rendering, the partial-failure path, and the input reset are all uncovered.
