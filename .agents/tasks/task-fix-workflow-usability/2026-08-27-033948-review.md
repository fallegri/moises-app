# Workflow usability remediation: shared AI-response field, state_of_art gating, and graceful AI-unconfigured degradation (v2)

The remediation commit (9cc6ed9) targets the five issues the v1 review left open. The backend now stamps a shared `ai_response` display field plus the raw `user_input` onto every phase result dict, catches `AIServiceConfigError` per phase (persisting the input, completing the task, and returning an advisory instead of a 500), and folds the state_of_art 6-studies rule into `can_advance` while exposing `advance_blocked_reason` through `GET /status`. The frontend reads `ai_response` first with per-phase key fallbacks, renders an amber advisory banner when the AI is unconfigured, surfaces `/advance` 400 details, and passes per-phase label/placeholder to `TextInput`. All five reported bugs are now resolved consistently across the backend contract and its frontend consumption, with tests that exercise the real code paths and would fail if the fix were reverted.

Watch for: nothing blocking. One cosmetic observation — when the AI is unconfigured on `problem_identification`, the green "guardado" banner and the amber advisory both render, which is slightly redundant (confirmed).

**Verdict**: APPROVED

## High-level view

The v1 root cause was a backend/frontend contract mismatch: the backend persisted per-phase result keys (`identified_problem`, `suggested_instruments`, `refined_formulations`, `research_questions`, `generated_content`) but the frontend renderer looked for `response`/`content`/`text`, so ten of twelve phases showed a saved banner and no AI text. The fix introduces a single `ai_response` display field written on every branch of `process_input`, and the renderer reads it first. The `identified_problem` dedicated block is retained without producing a duplicate because the generic block is guarded by `!identifiedProblem`.

The state_of_art disagreement between `can_advance()` (submission-only) and `advance_workflow` (6-studies rule) is resolved at the status layer: `GET /status` now calls `can_advance_state_of_art` and drops `can_advance` back to false with a specific `advance_blocked_reason` when the studies rule is unmet, so the button no longer enables into a guaranteed 400. `Project.tsx` additionally surfaces any `/advance` 400 detail as a red message, so even an unforeseen rejection is explained rather than silent.

The AI-unconfigured runtime is handled by catching `AIServiceConfigError` inside each phase branch: the raw input is persisted, the task is marked complete, and the result carries `ai_unconfigured`/`advisory_message`. `submit-input` returns 200 with the advisory promoted to the top-level message, so bug #5 (task check) and advancement keep working with no AI key. The coherence call remains separately guarded so it can never re-introduce a block.

Bugs #1 and #3 (vague copy, unclear upload purpose) were already addressed in the prior commit; this pass adds the missing per-phase `TextInput` label/placeholder via a `PHASE_TEXT` map, so every phase's text box reads specifically.

New tests exercise the real paths: the backend `AIServiceConfigError` tests inject a mock that raises and assert 200 + task completed + advance succeeds; the state_of_art status test asserts `can_advance` stays false with the studies reason and flips true once the flag is set; the frontend tests assert AI text renders for a `generated_content` phase, the `suggested_instruments` fallback works, the advisory banner and advance-error surface appear, and the per-phase copy renders. Each would fail if its corresponding fix were reverted.

### Shared ai_response field closes the render gap across all phases

`process_input` assigns `result["ai_response"]` on every branch — the AI text when configured, `""` with `ai_unconfigured`/`advisory_message` when not. `PhaseContent` reads it first:

```ts
const aiResponseText =
  (typeof phaseResult.ai_response === 'string' && phaseResult.ai_response) ||
  (typeof phaseResult.suggested_instruments === 'string' && phaseResult.suggested_instruments) ||
  ... generated_content ...
```

The per-phase key fallbacks are defensive against older persisted `phase_data` written before this commit (which lack `ai_response`), so a reloaded pre-existing project still renders. `problem_identification` keeps its dedicated highlighted block via `identified_problem`, and the generic block is gated by `!identifiedProblem`, so phase 1 renders exactly once. `test_process_input_sets_shared_ai_response_for_generated_content_phase` pins that `ai_response` mirrors `generated_content` for a chapter phase, and the frontend `renders the AI response for a generated_content phase` test confirms the text and the phase-specific `responseTitle` both appear.

### state_of_art gating no longer enables a button that 400s

`GET /status` computes the base `can_advance`, then for `STATE_OF_ART` re-checks `can_advance_state_of_art(project)` and forces `can_advance` false with a concrete `advance_blocked_reason` when fewer than 6 studies exist and the no-more flag is unset, so the status contract agrees with `advance_workflow`'s 400. The frontend disables the button on `can_advance` and prints `advance_blocked_reason`, and `Project.tsx` reads `advanceWorkflow.error.response.data.detail` into a red message so any residual 400 is still explained. `test_status_gates_advance_until_enough_studies` walks the full path — submit, assert blocked with the studies reason, assert `/advance` 400s, set the flag, assert `can_advance` flips true and the reason clears.

### AI-unconfigured degrades instead of 500ing

Each phase branch wraps its AI call in `try/except AIServiceConfigError`, setting `ai_unconfigured` and an empty response rather than propagating. The raw `user_input` is persisted unconditionally, the task is marked complete, and the coherence call is separately guarded so it cannot re-raise. `submit_input` promotes `advisory_message` to the response `message`. The result: no 500, the task checkbox marks (bug #5), and advancement works with no AI key. `test_submit_does_not_500_and_flow_can_advance` injects a raising mock at the router's engine and asserts 200, `ai_unconfigured`, task completed, and a successful advance to the next phase — the integration-level guarantee the v1 tests never exercised because they always mocked a working AI.

### Per-phase TextInput copy

`PHASE_TEXT` maps every `PhaseId` to a `label`, `placeholder`, and `responseTitle`; `PhaseContent` passes `phaseCopy.label`/`phaseCopy.placeholder` into `TextInput` ("Describe la situacion problematica" with an example placeholder) instead of the generic default, and `responseTitle` labels the AI-response block per phase. `renders a phase-specific TextInput label and placeholder` covers it.
