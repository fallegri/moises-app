# Workflow usability fix: submission-gated advancement, persisted status, and clearer per-phase guidance

The change reworks the guided research workflow so submitting a phase (not passing a coherence check) is what marks tasks complete, persists the AI result, and unlocks advancement. The backend now marks the current phase's task(s) completed on submit, stores the AI result on both `task.response_data` and `state.phase_data`, runs coherence advisorily, and exposes `phase_result`, per-task `response_data`, `last_validation_message`, and `phase_info.instruction` through `GET /status`. `advance_workflow` no longer 400s on a failed coherence check (it returns a non-fatal warning) while keeping the state_of_art 6-studies constraint. The frontend renders the saved-confirmation banner, the identified problem, the per-phase instruction, and the optional-upload note from persisted status so they survive react-query invalidation and page reload, and gates the advance button on `can_advance`. This directly targets the five reported bugs, but the AI-response rendering is wired for only one of twelve phases and the state_of_art advance path reintroduces the "button enables but advancing fails" problem for that phase.

Watch for: the persisted AI response only renders for `problem_identification` — for the other eleven phases the frontend reads result keys that the backend never emits, so bug #2 (visible, persistent AI response) is unfixed outside phase 1 (confirmed). In state_of_art, `can_advance` enables the button after submit but `POST /advance` still 400s below 6 studies with no UI explanation, re-creating bug #4 for that phase (confirmed). With no AI key configured, submit returns 500 and the whole flow stays stuck (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

Advancement gating moved from coherence to submission. `can_advance()` now returns true when the current phase's tasks are all completed (or `phase_data` has an entry) and it is not the last phase; coherence is advisory and auto-run inside `process_input` under a try/except so an unconfigured AI cannot deadlock the flow. This is a well-tested fix for bugs #4 and #5 at the phase-1 level and for the multi-task instrument phase.

The persisted-status contract is the backbone of the frontend fix: `GET /status` now carries `phase_result`, per-task `response_data`/`completed`, `last_validation_message`, and `phase_info.instruction`, and the frontend derives its banner, checkbox, and advance state from those fields instead of transient mutation state. This makes the confirmation and identified-problem survive reload — but only for `problem_identification`.

The generic AI-response renderer in `PhaseContent` looks for `response`/`content`/`text` keys that no phase produces; the real payload keys are `identified_problem`, `suggested_instruments`, `refined_formulations`, `research_questions`, and `generated_content`. Only `identified_problem` has dedicated rendering, so ten of twelve phases persist an AI result the user never sees.

The state_of_art 6-studies rule lives only in `advance_workflow`, not in `can_advance()`, so the two disagree: the button is enabled after a text submit, but the POST rejects with a 400 the UI does not surface.

The primary phase AI call in `process_input` is not guarded the way coherence is, so an unconfigured AI turns submit into a 500 and blocks the entire flow — the tests never hit this because they all mock the AI.

The phase and task copy rewrites address bugs #1 and #3, and the optional-upload note is consistent and always visible. One requested detail was dropped: `TextInput` is rendered with default label/placeholder rather than phase-specific text.

### AI response renders for only one phase

`process_input` writes a phase-specific result dict into `state.phase_data[phase.value]` and `GET /status` forwards it as `phase_result`. The frontend then tries to render the AI text generically:

```ts
const aiResponseText =
  phaseResult && typeof phaseResult === 'object'
    ? (typeof phaseResult.response === 'string' && phaseResult.response) ||
      (typeof phaseResult.content === 'string' && phaseResult.content) ||
      (typeof phaseResult.text === 'string' && phaseResult.text) ||
      ''
    : ''
```

No phase produces `response`, `content`, or `text`. The actual keys are `identified_problem` (problem_identification), `suggested_instruments` (instrument_suggestion), `refined_formulations` (problem_refinement), `research_questions` (research_question), and `generated_content` (all chapter/state_of_art phases). Only `identified_problem` has a dedicated block, so for eleven of twelve phases the AI output is persisted and returned by the API but never shown — the user sees the green "Informacion guardada exitosamente" banner and nothing else. Bug #2 ("mostrar la respuesta de la IA de forma persistente") is therefore fixed only for the first phase; `generated_content` alone covers seven phases. Mapping the renderer to the real keys (or emitting a shared display field from the backend) closes the gap.

### state_of_art: button enables but advancing 400s

`can_advance()` gates purely on submission and last-phase position:

```python
def can_advance(self) -> bool:
    current_idx = self.get_phase_index()
    if current_idx >= len(PHASE_ORDER) - 1:
        return False
    return self._current_phase_submitted()
```

The state_of_art-specific rule (>=6 studies or the no-more flag) lives only in `advance_workflow`, which raises a 400 when unmet. Because a text submit in state_of_art marks the task complete, `can_advance` returns true and the frontend enables the advance button — but clicking it hits the 400. The frontend `advanceBlockedMessage` only reacts to `can_advance`, so nothing explains the rejection, and the advance mutation has no error surface in `Project.tsx`. For the user this is bug #4 inverted into "the button is enabled but does nothing" on the one phase with an extra constraint. Either reflect the studies requirement in the status-level gating (so the button stays disabled with a clear message) or render the 400 detail.

### Coherence made advisory

`process_input` auto-runs `validate_phase_coherence` wrapped so a failing or unconfigured AI cannot block, `advance_workflow` converts a negative coherence result into a non-fatal `coherence_warning` instead of a 400, and `can_advance()` no longer consults `coherence_validated`. `_parse_coherence_result` still fail-closes to `False` on an ambiguous response, which is harmless now that it only drives the advisory message rather than gating. The tests pin the behavior: `test_can_advance_true_after_submission_even_if_incoherent` and `test_advance_does_not_require_coherence` assert advancement proceeds on an explicit `INCOHERENTE` mock, and `test_workflow_advances_with_coherence_warning` covers the integration path.

### AI-unconfigured runtime blocks the whole flow

The coherence call is guarded, but the primary phase AI call is not. `process_input` calls e.g. `self.ai_service.analyze_problem(...)` directly, and that raises `AIServiceConfigError` when no key is configured. `submit_input` wraps `process_input` in a broad `except` that re-raises as HTTP 500, so with no AI key a submit fails, no task is marked complete, nothing is persisted, and `can_advance` stays false — every one of the five reported behaviors stays broken in that runtime. The 500-on-error wrapper predates this change, but the briefing requires graceful degradation when AI is unconfigured, and the tests all mock `AIService`, so this path is never exercised. Catching the config error and persisting the user's raw input with an advisory message would let the flow proceed unblocked.

### Phase and task copy, optional-upload note

The `get_phase_description` and `_get_phase_tasks` rewrites give each phase a concrete "what to do / why" and a consistent optional-upload note (`Opcional: puede adjuntar documentos de respaldo (.docx, .xlsx, .md).`), addressing bugs #1 and #3, and `FileUpload` surfaces that note plus the backend `instruction` as the per-phase purpose. One FEAT-003 detail was dropped: `PhaseContent` renders `TextInput` with its default label/placeholder rather than passing phase-appropriate copy, so the text box reads the same generic label in every phase even though the `label`/`placeholder` props exist for per-phase wiring.

### Task completion does not leak across phases

`process_input` marks every entry in `state.current_tasks` completed, and `advance_phase` reloads a fresh task list for the new phase, so a completed checkbox never carries over. The read-only checkbox binds to `task.completed` from refetched status, fixing bug #5 for the single-task phases and the two-part instrument phase; `test_process_input_marks_task_completed_and_stores_response` and `test_status_returns_persisted_result_and_completed_task` cover it end to end.
