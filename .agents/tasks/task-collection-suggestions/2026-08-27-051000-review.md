# Server-side split of problem analysis and collection guidance (v2)

The v1 blocker was that `collection_suggestions` was aliased to the full phase-1 response, so the entire analysis rendered twice — once in the green "identified problem" box, once under the "Informacion que debes recopilar" heading that mislabeled it. This pass adds `_split_problem_and_suggestions` to the workflow engine: it locates the "Informacion que debes recopilar" marker (case- and accent-insensitive, tolerant of markdown heading/bold/list decoration), assigns everything before it to `identified_problem` and the section body after the heading line to `collection_suggestions`. The persisted `problem_description.identified_problem` now holds the problem-only text, which also cleans up the context fed to downstream phases. Both v1 issues are resolved and covered by new tests.

Watch for: the marker match keys off any line that, after stripping `#*_-:` decoration, *starts with* "informacion que debes recopilar" — a bullet or sentence in the problem prose that opens with that phrase would trigger an early split and truncate the problem while misclassifying the justification as suggestions (possible; requires the model to emit that phrase before the real section).

**Verdict**: APPROVED

## High-level view

The split happens server-side, which is the right seam: `identified_problem` and `collection_suggestions` now carry disjoint content, and the frontend renders each in its own block with no code changes to the render gate. The problem text appears exactly once on screen, and the mislabeled-heading problem from v1 is gone.

Storing the problem-only text in `problem_description.identified_problem` (rather than the full blob) is a real improvement beyond the UI fix: `_build_project_context` and the document export both read that field, so downstream phases and the exported chapter now receive a clean problem statement instead of the problem plus the recollection list.

The missing-marker fallback returns `(full_response, '')`, so a model that renames or drops the section keeps the whole analysis as the problem and hides the recollection block rather than mislabeling it — fail-safe, and locked in by a test. Degradation still normalizes `collection_suggestions` to `''` on an unconfigured/errored AI, matching how `ai_response` is handled, and the block stays hidden behind the amber advisory.

The one soft spot is the marker matcher's leniency: stripping leading list decoration means a bullet line that begins with the marker phrase also matches, so prose that references "informacion que debes recopilar" before the actual section would split at the wrong line.

## The split resolves the duplication and mislabel

`_split_problem_and_suggestions` takes the first line that (after accent/decoration stripping) starts with `informacion que debes recopilar` as the boundary: everything before becomes the problem, everything after that heading line becomes the suggestions. Excluding the heading line itself is deliberate — the frontend already prints "Informacion que debes recopilar para la siguiente fase" as its own `h4`, so the section body renders without a repeated heading.

The new `test_process_input_splits_problem_and_collection_suggestions` asserts the two blocks are disjoint (problem keeps "Problema identificado"/"Justificacion" and drops the bullets; suggestions keep only the bullets), and the frontend `does not duplicate the problem text` test asserts `getAllByText(problem)` has length 1 — a direct regression guard against the v1 double-render.

## Problem-only text improves downstream context, not just the UI

`identified_problem` is consumed by `_build_project_context` (line 720-722), which prefixes "Problema identificado:" and feeds it into later phases such as instrument suggestion, and by the document export in `documents.py`. Before this change that field held the whole blob including the recollection bullets; now it holds the problem-only split, so the context handed to subsequent AI calls and the exported chapter is a clean statement rather than problem-plus-list.

## False-positive risk in the marker matcher

The boundary check is:

```python
stripped = _strip_accents(line).strip()
stripped = stripped.strip("#*_-: \t")
if stripped.startswith(_COLLECTION_MARKER):
```

Stripping `-` and `*` means a list item like `- Informacion que debes recopilar del cliente...` is treated as the section heading, and `startswith` (not equality) means any line opening with the phrase matches. Feeding `"Problema X.\n- Informacion que debes recopilar del cliente\nJustificacion Y."` splits at the bullet: the problem becomes just "Problema X." and "Justificacion Y." is misclassified as suggestions. This depends on the model emitting the phrase in prose before the real section, which the prompt discourages, so it is a possible rather than likely failure — but it is the remaining sharp edge. Anchoring on an exact heading match, or excluding list-prefixed lines from marker detection, would close it.

## Test coverage

Backend adds the split assertion and the missing-marker fallback, and extends the unconfigured/error tests to assert `collection_suggestions == ""`. Frontend adds the list-renders case, the no-duplication case, and the hidden-on-`ai_error` case. Not tested: the false-positive marker-in-prose input described above, and a marker present with an empty body (heading but no bullets — verified manually here to return `('...', '')` and hide the block, but unpinned by a test).
